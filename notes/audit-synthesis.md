## The single biggest risk the tracker still does not address

The tracker is now an excellent instrument for making the verification layer honest, and almost silent on whether that layer ever reaches an agent or changes what an agent produces. Every gate the owner can currently pull — #1's nine (soon ~nineteen) correctness bugs, the schema freeze, the packaging fixes — measures partspec against itself. The only issue that would test the actual thesis, #30, has no harness, no trial count, no committed `evals/`, and until this pass no release label; the MCP server that would put partspec inside an agent's tool list has no extra, no entry point, and depends on a render verb that does not exist; the five authoring assets in epic #3 ship opinions with test coverage on their examples and none on their effect; and the boundary between partspec and build123d-mcp — the thing that decides whether this is a distinct product or a worse copy of one that already exists and already has published benchmark gains — is written down nowhere in the repo. The failure mode is not that partspec ships something wrong; it is that partspec ships something impeccably correct that no agent loop ever runs, and the tracker as constituted would report that outcome as a clean sweep of green epics. That is the project's own thesis turned on itself: silence about the agent reading as success.
